# Release

A version bump and a changelog entry in one commit, an annotated tag on it, then the tag's push. finish-branch step 8 reads this only when the user asked for a release, a tag or a version bump in this session. Under autopilot no release is cut: it parks with no release (why: the number is the user's call), and the run goes on.

1. Tooling: the project's own release tooling wins: a release script, changesets, semantic-release, or a release section in CONTRIBUTING or the README. Follow it and say which; the steps below fill only what it leaves out, and the Bump's confirm and the Push's ask still hold.
2. Bump: `git describe --tags --abbrev=0` prints the last tag (it fails with none: this is the first release, and every commit is a change); `git log --oneline <tag>..HEAD` lists the changes since it. Choose by semver: a breaking change is major, a new feature minor, fixes only patch; below 1.0.0 a breaking change bumps minor. State the bump with the change that sets it, then wait: the user confirms the number before anything is written.
3. Changelog, for humans: one dated entry under the version, in the changelog's existing format; with none, `CHANGELOG.md` with Keep a Changelog's Added, Changed, Fixed, Removed under `## [<x.y.z>] - <YYYY-MM-DD>`. Write user-visible effects, breaking changes first, each with its migration step; never a commit-log dump.
4. Commit: the version in every manifest that carries one, plus the changelog entry, as one release commit, through commit's steps 2 to 6 as step 8 runs them. It changes the tree, so step 10's proven-tree check runs `test.full` on it.
5. Tag: `git tag -a v<x.y.z> -m "<x.y.z>: <one line>"` on that commit, never a lightweight tag; the line holds no `"`, `$` or backtick. The tag is the version's source of truth: each manifest's version matches it. Never move or reuse a pushed tag; a bad release gets the next patch.
6. Push: pushing the tag publishes it, so it is asked like any push, after step 10's branch push: `git push origin v<x.y.z>` as its own call, never `--tags`. G1 asks for it under `push.policy: auto` too (it allows only a branch push unasked), and that prompt is the ask; G1 denies it under `push.policy: deny` and under autopilot. Declined, or with option 1, the tag stays local: report it and go on. A rejected tag push means the remote has that tag: stop and report; never force it.
