M2a: the workflow, with its gates in code

M2a builds kern's working loop: define a change, plan it, run it task by task in worktrees with a review of each task, prove it, commit it and open a draft PR. Where the M2 plan trusted the model, M2a puts a script or a guard in front of the step, with a test that fails first. M2b, next round, proves the result beats the sources.

How M2a works

One change, from request to draft PR

Each stage is a skill. The blue line under it is the check that runs as code, not as an instruction to the model.

define

Clarify the ask, write a spec with a Constraints section, get your explicit yes.

G20 checks your quote

plan

Slice the spec into tasks with exact files, interfaces and tests.

plan-check --graph

execute-plan

Open a ledger, brief each task, run it in its own worktree.

ledger-open · brief-check

implement

Write the failing test first, then the code, inside the task's worktree.

probe: fails, then passes

review per task

A read-only reviewer judges the exact tree, with no commits needed.

task-done refuses an unreviewed tree

self-review

Spec lane, blast radius, floor scan, a doubt pass in fresh context.

floor-scan · claim-check

commit

One commit per reviewed task, message in the convention you use.

G5 proven shape

finish-branch

Push the proven tree, open a draft PR, never merge.

G1 · G2 draft and dedup

Around the loop: diagnose for bugs, parallel-work for independent tasks in forks, recall to rebuild state after a break, and prove-it before any "done".
