Personal Agent Framework Design

One Claude Code plugin that takes the strongest mechanism from superpowers, pstack, mattpocock/skills and addyosmani/agent-skills in each category, plus caveman's terse voice, and runs the same way in every project you open.

fw is a placeholder until you pick a name (decision 1). Each section ends where you can approve it or ask for changes.

Revision 2. The project settings file is now local and untracked by default. Five skills load automatically instead of nine; the kernel routes to the rest. Autopilot turns on only from a command you type, and a guard stops Claude from switching it itself. The guard table now shows interactive and autopilot behaviour side by side.

Revision 3. take-feedback gains rebase and drive modes and works with stacked PRs: GitHub's gh stack first, plain git rebase --update-refs as a fallback, single PRs by default. A new guard, G17, gates every gh stack command.

Revision 4. Review runs Claude Code's built-in code-review as one lane beside the framework's own reviewers, then merges and verifies the findings. See the new pr-review panel in section 3.

Revision 5. html mode is visual pages, not a portal. A page replaces text when options, variants or a design are easier to see. Questions on a page can be answered there, and Claude carries on without a trip to the terminal, or answered in the terminal as usual.

0 · Understanding

What this is for

What you said

  • Your own framework, built by categorizing every skill in the four plugins and combining the strongest parts.
  • Wide (every phase of the work) and deep (rigorous within each phase).
  • A personal plugin in its own repo, portable across all your projects. Not CDS-specific.
  • Claude Code only.
  • Gated by default, with an opt-in autopilot per session.
  • Three modes: caveman-style terse, html for visual pages (options, variants, designs) you can answer on the page or in the terminal, and auto as the default.

What I assumed

  • Each project's CLAUDE.md, rules and own skills win over the framework.
  • Depth lives in on-demand reference files, so "wide" does not cost context every session.
  • The framework tests itself in CI, and a learning loop turns repeated mistakes into checks.
  • All four sources are MIT and caveman is Apache-2.0, so their text can be reused with attribution. The caveman name is a trademark and is not reused.
  • Superpowers stays installed until the framework can do its job.

Done looks like: one install on any machine. One router. Every superpowers job still covered, plus pstack's proof discipline, mattpocock's debugging gate, addy's specialist skills and evals, and visual pages for options, variants and designs that you can answer by clicking.

pr-review: four lanes, one merged result

The built-in code-review is strongest on correctness bugs, and it already runs as its own background subagent. The framework's reviewers cover what it does not look for: the spec, the project's rules, design, tests and security. They run side by side, and their findings merge into one list.

Merge
  • Findings are deduplicated by file, line and claim, and each one keeps the lanes that raised it.
  • A finding two lanes agree on goes straight in.
  • A finding from one lane only, the built-in included, gets a verify pass first: a fresh subagent tries a fail-then-pass probe (G10). Unproven findings are listed separately as "plausible". The local built-in has no documented verify pass of its own, so the framework supplies one.
  • The result uses the project's labels (review.taxonomy), and in html mode becomes a visual page with one card per finding.
Rules for the built-in lane
  • Always pass an explicit effort and --max-findings. The built-in remembers the last values typed, even across sessions, so leaving them out gives different results run to run. Side effect: your own later manual /code-review runs may reuse the framework's values; --max-findings default resets that one.
  • Never --comment from inside a review. It posts to the PR immediately, with no confirmation. Posting goes through the framework's draft and approval step instead (G3). --fix only runs in a worktree, from take-feedback, after you pick which findings to fix.
  • Round 1 runs all lanes. Round 2 and later run the built-in alone on <last-reviewed>...HEAD, at a lower effort. The spec lane re-runs only if the spec changed.
  • self-review runs the built-in at low effort on your uncommitted diff before a PR exists.
  • If the built-in is missing, lanes B to D run alone. The built-in /security-review can be added as lane E with review.builtin.security: on.

take-feedback: modes and stacked PRs

ModeWhat it doesEnds at
checkRead-only status: checks, threads, mergeability. For stacks, gh stack view --json shows which layers need a rebaseA report

Stack providers, picked by stack.tool or detected
  • gh-stack, GitHub's stacked PRs extension: gh stack rebase for the cascade, --continue or --abort on conflicts, then gh stack sync, which pushes every branch atomically with --force-with-lease. New PRs go through gh stack submit --auto, which opens them as drafts.
  • git, for stacks without a tool: git rebase --update-refs moves every branch in the chain in one pass, and gh pr edit --base fixes the chain after a layer merges.
  • none, the default: single PRs, plain git rebase onto the base branch.
  • Graphite or git-spice adapters can be added later behind the same five steps: view, rebase, continue or abort, push, submit.
Rules for stacks
  • Work the lowest unmerged PR first. Fix a finding in the lowest branch that owns the code, then cascade upward. Upstack threads wait for the next push wave.
  • One stack, one worktree. gh stack checks branches out as it rebases, so stack commands never run in your main checkout, and no other worktree may hold a stack branch.
  • Mechanical conflicts (imports, formatting, adjacent edits) are resolved. A conflict where both sides changed behaviour stops the rebase with --abort, which restores every branch, and goes to you with a conflict report.
  • After a rebase, each layer's patch-id is compared (G11). An unchanged patch-id keeps its review verdict; a changed one is re-tested and re-reviewed on the delta.
  • Pushes use --force-with-lease only, and only on your own non-protected PR branches. A branch with another author's commits counts as shared and is never force-pushed.

Tightening: the highest source wins. Loosening a safety default: only a settings key can do it, so hooks and skills always agree. The floor never loosens: merge, production deploy, data deletion, force-push to a shared branch, and messaging people always need you. A step a project rule overrides stays in the todo list as skip: <rule> overrides. No agent's message counts as your consent.

How routing works

Before the first tool call of a new task, match it against the table. Rows key on things Claude can observe, such as "a bug, failing test or unexpected output" or "about to say done, open a PR or commit", not a vague "1% chance a skill applies". On a match, read the route in full, then open a todo list whose first items are its steps, copied verbatim. Several matches resolve in order: define and diagnose before build.

5 · Modes and visual pages

Voice and surface, per session

The mode is two settings, voice and surface. Presets cover the three you asked for, and they combine.

/fw:mode auto

The default. Normal voice and text in chat. A visual page only when seeing beats reading: three or more options or variants to compare, a design to preview, a diagram, or a table over about 10 rows.

/fw:mode terse

Caveman-style voice for the whole session: answer first, no filler, payload verbatim. Rules adapted from caveman (Apache-2.0, with attribution). Named terse because "caveman" is a trademark.

/fw:mode html

A visual page instead of text whenever an answer has options, variants, a design to show, or structure such as a plan or a set of findings. The chat keeps a short summary and the link. Security warnings and irreversible-action confirmations always stay in chat.

/fw:mode html terse

Both. Pages stay in plain prose; only the chat is terse.

How the mode sticks

  • State per session, keyed by session id, under ${CLAUDE_PLUGIN_DATA}. It survives compaction and resume; /clear and new sessions reset to your default.
  • SessionStart injects only the active mode's rules. UserPromptSubmit applies switches, adds a short reminder outside the default mode, and passes in any page answers Claude has not seen yet.
  • Natural-language switches ("go terse", "stop html") work, with guards against negations and questions.
  • Optional status-line badge. A plugin cannot add a status line, so help setup prints a two-line snippet for your settings.
  • /fw:autopilot on works the same way: the hook reads it from the prompt you type. Claude cannot invoke a slash-only skill, and guard G16 denies any tool call that writes to the mode state directory, so Claude cannot turn autopilot on by itself.

What a visual page is

  • A page in place of a block of text, when visuals help: options side by side, UI variants and mockups, a design to look at before it is built, a diagram, a comparison table.
  • One page per output. Not an app: no dashboard, no navigation, no driving Claude Code from the browser.
  • Claude writes the content; the framework wraps it in one design system with light and dark themes, option cards, variant frames and diagrams.
  • Pages are files in the working directory, so you can reopen any of them later.

Answering on the page or in the terminal

  • When a page asks something, it shows the choices, a note field and a Send button.
  • Answer on the page: press Send and Claude carries on by itself, with no trip back to the terminal. While a page waits, Claude runs a small background command that ends the moment you send. Claude Code resumes Claude when a background command ends, and the command hands over your answer.
  • Answer in the terminal: type as usual. Claude stops waiting, uses what you typed, and the page marks the question as answered.
  • The page talks to a tiny local server, started only when a page has a question. It listens on 127.0.0.1 only, puts a random key in the URL, makes no network calls, and stops when idle or when the session ends. Adapted from superpowers' visual companion (MIT), without its tracking beacon.
  • No node, or an SSH session: the page opens as a static file and you answer in the terminal.

6 · Safety and autopilot

7 · Project profile

How each project plugs in

A flat key: value file, readable by both skills and bash hooks. Anything the repo can show (base branch, test commands, commit style) is detected; the file only overrides it. /fw:help setup proposes the rest and writes the file only after you confirm.

Three files, later ones winning
  • ~/.claude/fw.yml: your defaults across all projects, and fw_repo, the path to your plugin checkout for framework fixes.
  • .claude/fw.yml: optional and shared. Committed only if a team wants it.
  • .claude/fw.local.yml: the default. Kept untracked through .git/info/exclude, so the framework never adds a file to a team's repo.
Keys, grouped
  • Repo: base_branch, worktree.setup, shared_services, work_dir
  • Checks: test.focused, test.full, typecheck, lint, verify.fast, verify.browser
  • Git: commit.convention, commit.policy, branch.pattern, push.policy, pr.policy, pr.template
  • Stacks: stack.tool (gh-stack, git or none; detected when unset), rebase.push (ask by default, autopilot to allow lease pushes under autopilot)
  • Review: review.taxonomy, review.rounds, review.rules, review.sensitive_paths, security.rules
  • Built-in review: review.builtin (on by default), review.builtin.effort (high), review.builtin.delta_effort (medium), review.builtin.max_findings (15), review.builtin.security (off)
  • Work tracking: tracker, tracker.first, spec.source
  • Risk: autopilot, allow, scope_threshold, protected_targets, deploy.envs, deploy.proof, never_commit
  • Learning: lessons (where this project's lessons go), rule_bar
  • Overrides: overrides.<job> names a project skill that replaces a framework skill
  • Stack: stack picks reference files such as stacks/typescript.md or stacks/go.md
Example: CDS, in .claude/fw.local.yml
tracker: linear

Base branch and test commands are detected, so they are not listed. CDS keeps its own pr-review and commit skills; the framework defers to them and its hooks still apply. The file is untracked, so CDS's repo does not change.

Working files (specs, plans, ledgers, visual pages) default to $(git rev-parse --git-common-dir)/fw/. Every worktree of the repo shares that directory, git never tracks it, and no .gitignore edit is needed. A project can set work_dir: docs/specs to keep specs in the repo instead.

8 · Quality and learning

The framework tests itself

In the plugin repo's CI

  • Lint on every PR. 14 rules: Claude Code frontmatter keys, description limits per tier, kernel routes that point at real files, size budgets, hook output shape, claude plugin validate --strict.
  • Routing evals on every PR. Adapted from addy: each skill has prompts that should and should not trigger it, and your other installed skills act as distractors. The pass floor only rises.
  • Behavioral evals, nightly or on demand. claude plugin eval cases with the model pinned, superpowers-style pressure tests, and a kernel-adherence grader that checks the first todo list matches the route's steps.

The learning loop

  • A correction or repeat in any project routes to /fw:retro or /fw:correct.
  • Project-specific lessons land in that project's rules, under its own bar for adding rules.
  • Framework lessons become a change to a skill or a guard in the plugin repo, shipped with an eval that fails before and passes after.
  • Prefer a check to more prose: architecture, then types, lint, tests, docs. Once a check enforces something, delete the prose rule.
  • Rejected changes go in an out-of-scope ledger so they are not proposed again.

10 · Decisions

Five calls for you, each with a recommendation

1. The framework's nameIt becomes the slash prefix (/name:define), the profile file name and the repo name. Short and easy to type works best. No recommendation; your call.
2. Terse voice: own mode or keep the caveman pluginRecommended: own terse mode, then uninstall caveman. Two plugins tracking mode state would fight; caveman would keep injecting after you switch to html.
3. Where working files liveRecommended: the git common directory, shared by all worktrees, never tracked. Alternatives: a .fw/ folder excluded through .git/info/exclude, or docs/specs committed when you ask.
4. Repo visibilityRecommended: private GitHub repo with its own marketplace file, so any machine installs it with two commands. Public later is possible; the NOTICE file already covers attribution.
5. Scope of the first buildRecommended: M0 to M2 first, pilot it, then decide on M3 to M6. M2 already replaces superpowers.
